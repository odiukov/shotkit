# Role-labelled references (`refKit`) — reference

A character's `refKit` (in `bible.json`) is a list of reference images, each an entry
`{uri, role, note}`. The `role` tells the render what that one image supplies and what
it must be ignored for — this file is the vocabulary.

## Why role travels as text, not as an API field

No image-generation API lets you declare "this attached image is the face" or "this one
is the garment" as a structured field — an attached image is bytes and a mime type, full
stop. What these APIs support instead is addressing an image by its **position**: "take
the dress from the third image." So a role has to travel as prose, in a manifest that
numbers every attached image in order — and that only works if the reference images you
actually attach to the render arrive in **exactly** the order the manifest numbered
them. Get the order right, or every role is talking about the wrong photo.

**This is why `shotkit sheet`'s two output files are a matched pair:
`out/characters/<id>/<look>.sheet.txt` is the prompt with the numbered manifest baked in,
and `out/characters/<id>/<look>.sheet.refs.txt` is the reference list in that same
order** (or, with `--handoff`, the same pairing printed as one block instead of two
files). Attach them to your image model in the file's order, not the order you happen
to have the images open in.

## The six roles

| Role | What it takes | What it must ignore |
|---|---|---|
| `face` | bone structure, eyes, nose, mouth, skin tone and texture | clothing, background, pose, framing |
| `body` | body build and proportions only | clothing; face (comes from the face slot, or the identity description if there is none) |
| `hair` | hairstyle and hair colour only | face, body, clothing |
| `outfit` | the garment — cut, colour, fabric, details, read as a catalogue product shot | whoever is wearing it: they are a mannequin, not the subject |
| `object` | an object, reproduced with high fidelity | everything else in the image, including any person in it |
| `full` (wire value `full`; shown to a person as **"whole"**) | a whole reference photograph, read for identity | — nothing excluded; this is the "just use the photo" role |

An unrecognised or missing role degrades to `full` rather than raising an error — a
role typed by hand or generated by a script should never be able to break a render by
being unrecognised; `full` is also the exact behaviour a reference had before roles
existed.

## Two independent counting buckets

Reference-conditioned image models commonly count references toward **two separate
caps**, and the roles split cleanly along that line:

- **Character-consistency references** — `face`, `body`, `hair`, `full` — anything that
  supplies an aspect of who the subject is.
- **Object-fidelity references** — `outfit`, `object` — anything that supplies a thing
  to be reproduced exactly, worn or held by someone who is not the subject.

A garment photo must be tagged `outfit`, not left as a bare `full` reference — untagged,
the model reads the photo the ordinary way, as a photo of a person, and treats **that
person** as the subject to reproduce, not the coat they're wearing. Asking for it
explicitly as an object is what redirects the model's attention to the garment and away
from its occupant.

`shotkit`'s `validate_ref_kit` (in `shotkit/ref_kit.py`) checks a slot list against a
target model's caps — a max for the character bucket, a max for the object bucket, and
optionally a max for the whole set — and raises rather than silently trimming. It isn't
called automatically by `shotkit sheet` (shotkit has no built-in per-model catalog of
caps, since it's meant to work with whichever generator you're pointing it at); call it
yourself with your target model's numbers before you spend a render on a kit you suspect
is oversized. Refusing beats trimming here for a specific reason: a model that silently
drops the surplus reference still produces *a* render, and a correct-looking render of
the wrong reference set reads to a human as "the outfit slot did nothing" — a much
harder bug to notice than an upfront refusal naming the exact count and the cap it
exceeds.

## The worked failure this manifest exists to stop

This mechanism exists because of an observed failure on a real render. A character's
`refKit` held a face reference and several full-body panels, plus one `outfit` reference
— a coat, photographed on a man, because that was the only full-length human photograph
available for the garment. The face panel rendered correctly: it took the face reference
as intended. But **every full-body panel came back wearing that man's face and that
man's build** — the model had used the only full-length human image in the kit as its
template for "what a full body looks like here," and the occupant of that photo came
along with it.

The per-slot instruction to ignore the coat photo's wearer was present — one clause
inside that one slot's entry — and it lost, against nine full-body panels all pulling
from the same wrong template. The fix wasn't a stronger per-slot clause: it was
restating the rule once more, **last**, for the whole sheet — "the garment and object
images above are PRODUCT references; whoever wears or holds them is a mannequin and
contributes no face, no hair, no body build and no pose to any panel" — naming exactly
which slot the real face and body come from instead. Primacy (the manifest header, read
first) plus recency (this closing restatement, read last) is what a single embedded
clause could not do on its own.

The practical lesson: whenever a kit includes any `outfit` or `object` slot, treat the
occupant-bleed risk as real, and make sure your prompt (or, if you're building this
manually rather than through `shotkit sheet`, your own manifest text) restates once, for
the whole sheet, exactly which slot the face and body actually come from.
